Windows 10 and Windows 11

Local hardware control that installs predictably.

A two-PIN Windows Service for USB-storage and mobile-device control with opt-in screen-snapshot monitoring. This guide is written for both office administrators and the people who support the PCs.

Start Here

Local device protection works offline; snapshots & remote need Supabase. The desktop talks to the service via local IPC; the service syncs to Supabase when cloud credentials are installed at setup (env vars or cloud-credentials.json — never baked into this ZIP). See Remote Management for DB access.

Package contents

  • SecureDeviceControl.Desktop.exe: administrator interface and snapshot capture agent (virtual-screen JPEG, max 1920px, quality 70).
  • SecureDeviceControl.Service.exe: privileged Windows Service — enforces policy and validates/uploads snapshots.
  • SecureDeviceControl-Dashboard.zip (separate download): admin dashboard for Supabase bucket review — device/date organized, deduped by perceptual hash.
  • install-service.ps1: approved installation and repair script.
  • Install-Service.cmd: convenience launcher for the installer.
  • uninstall-service.ps1: PIN-authorized removal script.
  • documentation.html: this guide (also inside the dashboard ZIP).

Before deploying to 50 PCs

  • Test the package on two representative non-production PCs.
  • Use a Windows administrator account for installation.
  • Give ordinary employees standard-user accounts, not local administrator rights.
  • Create different, non-reused six-digit PINs for each PC.
Important: this release ships with NO secrets — appsettings.json holds only the project URL, bucket name, and public anon key. Cloud credentials are installed per-PC at setup (see Remote Management). The service_role key lives only on the admin dashboard PC. Rotate it in Supabase Dashboard if a previous ZIP (which baked the key) ever leaked, then discard old ZIPs. Keep every ZIP private for the 50-PC rollout.

Install And Repair

The desktop application does not create a Windows service or request elevated access itself. This is intentional: service installation is an explicit, auditable administrator action.

Normal installation

  1. Extract SecureDeviceControl-Release.zip to a local folder.
  2. Open PowerShell with Run as administrator.
  3. Run the following commands from the extracted folder.
Set-Location "C:\Path\To\SecureDeviceControl-Release"
Unblock-File -Path .\*
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\install-service.ps1
sc.exe query SecureDeviceControl

The expected result is STATE : 4 RUNNING. The installed service runs as LocalSystem and its binary is copied into C:\Program Files\SecureDeviceControl.

Repair this specific startup failure

Use this only when Event Viewer reports SQLite Error 14: unable to open database file, or when the old package created both SecureDeviceControl and Secure Device Control.

Set-Location "C:\Path\To\SecureDeviceControl-Release"
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\install-service.ps1 -MigrateLegacyService -ResetLocalData
sc.exe query SecureDeviceControl
What repair changes: it removes only the obsolete duplicate service and moves existing secure-device-control.db, -wal, and -shm files into a timestamped C:\ProgramData\SecureDeviceControl\recovery folder. It does not delete them. You will need to create the two PINs again after a reset.

Validate the installation

Get-Service SecureDeviceControl | Format-List Name,Status,StartType,DisplayName
sc.exe qc SecureDeviceControl
Get-WinEvent -FilterHashtable @{ LogName = "Application"; StartTime = (Get-Date).AddMinutes(-10) } |
  Where-Object { $_.Message -match "SecureDeviceControl|SQLite Error" } |
  Select-Object TimeCreated, Id, LevelDisplayName, Message |
  Format-List

Snapshot Monitoring OPT-IN · RATE-LIMITED

What it does: when enabled, the desktop app captures the virtual screen (all monitors composited) and asks the local service to upload a JPEG to private company storage. The service — not the desktop — is the gatekeeper: it checks registration, explicit acknowledgement, the enabled flag, JPEG validity, and the interval before any upload. If any check fails, the upload is rejected and an activity log entry is written.

How it is turned on

  1. During first-run registration (First-run Registration & PIN setup) tick:
    I understand that this company-owned PC will capture screen snapshots every 5 minutes by default …
  2. Click Initialize & Register. The service stores three settings: snapshot_monitoring_acknowledged (true only if ticked), snapshot_enabled=true, snapshot_interval_minutes=5.
  3. The desktop calls SnapshotStartupRegistrar.EnableForCurrentUser() which writes HKCU\Software\Microsoft\Windows\CurrentVersion\Run → SecureDeviceControlDesktop="<Desktop.exe>" --snapshot-agent. On next sign-in the desktop starts minimized (App.xaml.cs --snapshot-agent → MainWindow(startMinimized)) and resumes capture without user interaction.
  4. If the box was not ticked, the same three settings are stored as acknowledged=false and every upload is rejected with Unauthorized until an administrator re-registers with acknowledgement.

What is captured & how

  • Capture: SnapshotCaptureService.CaptureVirtualScreenAsJpeg() — SystemInformation.VirtualScreen → 24bpp bitmap → scaled so the long edge ≤ 1920 px → JPEG quality 70 via ImageCodecInfo. Throws if no active screen.
  • Interval: default 5 min, clamped 1–120 min. The service enforces now - last_snapshot_uploaded_at < interval → RateLimited. The desktop also throttles locally and polls every 30 s.
  • Validation (service: DeviceControlCoordinator.UploadSnapshotAsync): must be registered; acknowledged==true && enabled==true; JPEG magic FF D8 … FF D9; 4 B – 8 MB; PC-name object key generation; storage available.
  • Object key: {PC-NAME}/{yyyy}/{MM}/{dd}/{yyyyMMdd-HHmmss-fff}.jpg where the folder is the sanitized Windows computer name (see SnapshotObjectKey). Time is TimeProvider.GetUtcNow().
  • Storage: ISnapshotStorage → SupabaseSnapshotStorage (DI in Program.cs: ISnapshotStorage, SupabaseSnapshotStorage) uploads to Supabase Storage bucket Snapshots. Success → last_snapshot_uploaded_at = now:O + SnapshotUploaded log; failure → SnapshotUploadFailed + warning.

Using it day-to-day

  1. Keep the desktop running. After registration, SecureDeviceControl.Desktop.exe auto-starts at sign-in (Run key + scheduled task). After shutdown/reboot the Windows service re-applies port/web/VPN/mail policy and relaunches the snapshot agent in the signed-in session. Closing the tray icon pauses capture until the service starts it again.
  2. Check status: Refresh calls GetServiceStatus which returns SnapshotEnabled, SnapshotIntervalMinutes, SnapshotMonitoringAcknowledged. The desktop forwards these to snapshotCaptureService.UpdateSettings() — no separate UI toggle; interval is policy-controlled (change snapshot_interval_minutes in the service DB if your policy needs it).
  3. Verify uploads: Load logs → look for SnapshotUploaded (“A screen snapshot was uploaded to company storage.”) and SnapshotUploadFailed. Each attempt is also subject to the service rate-limit message: The next snapshot is not due yet.
  4. Change interval (advanced): an administrator with DB access can update snapshot_interval_minutes via the service IPC/database layer; the next Refresh picks it up. Values outside 1–120 are clamped.
  5. Disable: set snapshot_enabled=false or snapshot_monitoring_acknowledged=false in the service DB, or remove the Run value SecureDeviceControlDesktop. The service will then reject uploads with Unauthorized: Screenshot monitoring is not enabled.
Employee notice: only enable snapshot monitoring on company-owned PCs where employees have been informed per local law and company policy. The registration checkbox text is the explicit acknowledgement record. For the 50-PC rollout, include this notice in your deployment checklist and keep the desktop autostart enabled.

Admin Dashboard — Reviewing Snapshots SEPARATE ZIP

The dashboard is a second ZIP (SecureDeviceControl-Dashboard.zip) — a self-contained single-file WPF app (net8.0-windows, single-file, self-contained, artifacts/dashboard/SecureDeviceControl.Dashboard.exe). It does not install a service; it only reads from Supabase.

First run & login

  1. Extract the dashboard ZIP and run SecureDeviceControl.Dashboard.exe. On first run you create an Admin ID + password (PBKDF2-SHA256, 100 000 iterations).
  2. Credentials are stored in %LocalAppData%\SecureDeviceControlDashboard\settings.json with the service-role key DPAPI-protected. No key is stored in the repo.
  3. Open Settings and enter your Supabase URL (https://…supabase.co) and service_role key. The dashboard validates https.
  4. Run self-test any time: SecureDeviceControl.Dashboard.exe --selftest — checks key parsing, PC-name storage prefix, perceptual-hash, session grouping, and password hashing (7 checks, exit 0 on PASS).

How the gallery works

  • Devices: SupabaseSnapshotClient.GetRegisteredDevicesAsync() paginates rest/v1/registered_devices?select=email_id,machine_name,updated_at (page 500) and computes deviceHash the same way as the service for matching.
  • Snapshots: Storage API storage/v1/object/list/Snapshots with pageSize 1000; each object key is parsed by SnapshotEntry.TryParse("{hash}/{yyyy}/{MM}/{dd}/{yyyyMMdd-HHmmss-fff}.jpg") (19-char time part — fixed from the earlier 15-char bug).
  • Organization: grouped by deviceHash → calendar date → time-sorted.
  • Dedup / sessions: local dHash (64-bit, 9×8 resize, grayscale, horizontal gradient, HammingDistance via BitOperations.PopCount). SnapshotSessionizer.GroupSessions(frames, threshold: 8) collapses consecutive near-duplicates into a SnapshotSession (StartUtc, EndUtc, FrameCount, thumbnail). Idle desktops collapse to one session; a full screen change (distance > 8) starts a new session.
  • Viewer: session cards show device/email, date, time range, frame count, thumbnail; click to open ViewerWindow with full JPEG.

Daily use

  1. Pick a device (by email/machine → hash) and a date. Sessions appear already deduped — a 4-hour idle period may show as one session with FrameCount=48 instead of 48 identical rows.
  2. Use the dashboard on one admin PC; it needs only the Supabase URL/key — no install on the 50 monitored PCs.
  3. Rotate the Supabase service_role key periodically; update it in Settings (DPAPI-protected). If the Groq or Supabase key was ever pasted in chat, rotate it immediately.
Tip for 50 PCs: deploy the main release ZIP to all PCs (service + desktop with autostart). Give the dashboard ZIP to only the 1–2 reviewers who need to audit snapshots. They run the exe with no install friction — single file, no dependencies.

Permissions And Security

What receives privilege

Only SecureDeviceControl runs with LocalSystem rights. It owns registry policy changes and local audit storage. The desktop app has no code path that creates, stops, or changes the service.

Protected locations

C:\Program Files\SecureDeviceControl and C:\ProgramData\SecureDeviceControl grant full control to SYSTEM and local Administrators. Standard users do not receive write access.

  • PINs use Argon2id hashes and DPAPI-protected records.
  • PIN attempts are rate-limited after repeated invalid entries.
  • Service restarts are configured through Windows Service Control Manager recovery actions.
  • Windows administrators can still disable or remove third-party software. This product resists standard-user bypasses; it does not claim to be impossible for an unrestricted administrator to bypass.

Activities And Testing

Use the desktop app's Load logs action after validating the service. Local activity records include service starts, PIN validation events, policy changes, temporary unlocks, detected removable-drive writes, and snapshot events (SnapshotUploaded / SnapshotUploadFailed).

Release acceptance test

  1. Install on a test PC using the normal installation commands.
  2. Verify the service is running and the desktop reports Needs Registration.
  3. Set two distinct PINs — tick the snapshot acknowledgement box if you want to test snapshots — attach a test pendrive, and verify it is blocked.
  4. Unlock for 15 minutes with the Device Unlock PIN and verify access.
  5. If snapshot monitoring was acknowledged: keep the desktop running for 6 minutes, then Load logs and verify a SnapshotUploaded entry; check Supabase Storage bucket Snapshots for key {hash}/2026/…/{yyyyMMdd-HHmmss-fff}.jpg. If not acknowledged, verify uploads are rejected.
  6. Open SecureDeviceControl.Dashboard.exe (separate ZIP) with your Supabase URL/key, pick the test device/date, and verify the new snapshot appears as one session (deduped via dHash).
  7. Restart Windows, then verify the service starts automatically, the policy is restored, and — if acknowledged — the desktop reappears minimized and resumes snapshots.
  8. Enter an incorrect PIN five times and verify the temporary lockout.
  9. Use the Uninstall PIN flow only on a disposable test machine.
The automated suite validates policy logic, PIN rules, rate limiting, IPC session checks, and stress loops. It does not replace live hardware, reboot, service-account, or standard-user tests on your actual Windows image.

Change either PIN remotely (no target access)

Yes — both the port-blocking PIN (Device Unlock) and the Uninstall PIN can be changed from Supabase. The target polls remote_commands every 30 seconds (SupabaseSyncWorker.cs:159) matched on email_id + machine_name, validates the payload is a six-digit PIN, re-hashes it locally, and marks the row COMPLETED (or FAILED with a reason).

-- Port-blocking PIN (Device Unlock) — command is UPDATE_DEVICE_PIN (alias UPDATE_UNLOCK_PIN):
INSERT INTO remote_commands (email_id, machine_name, command, payload)
VALUES ('new-employee@company.com', 'NEWPC-NAME', 'UPDATE_DEVICE_PIN', '482917');

-- Uninstall PIN:
INSERT INTO remote_commands (email_id, machine_name, command, payload)
VALUES ('new-employee@company.com', 'NEWPC-NAME', 'UPDATE_UNINSTALL_PIN', '730451');

-- Confirm (within ~30 s, sooner after Restart-Service on the target):
SELECT id, command, status, error_message, executed_at
FROM remote_commands
WHERE email_id = 'new-employee@company.com'
ORDER BY id DESC LIMIT 3;
  • Rules: payload must be exactly six digits and different from the other PIN; otherwise the row goes FAILED — Invalid PIN payload and nothing changes.
  • Verify: status=COMPLETED plus a local [REMOTE CMD] Remote Device Unlock/Uninstall PIN update applied. activity entry. The old PIN stops working immediately.
  • Stuck at PENDING? the PC is offline, on service < 1.0.0, or the email_id/machine_name does not match its registration — see #support.
Security: service_role bypasses RLS — keep appsettings.json ACL SYSTEM+Administrators only (install-service.ps1:22). This ZIP ships pre-configured for the 50-PC rollout, so keep the ZIP itself private; rotate keys in Supabase Dashboard if leaked and rebuild.
